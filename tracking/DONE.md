Mientras solo existía una cuenta de admin creada a mano, esto era inofensivo; en cuanto se permite que cualquier visitante cree su propia cuenta (`createUserWithEmailAndPassword`), esa misma condición le habría dado acceso administrador total (editar catálogo, ver/gestionar todos los pedidos, TPV) a cualquier cliente recién registrado. Redefinido: `isAdmin()` ahora exige `exists(/databases/$(database)/documents/admins/$(request.auth.uid))`. Migración: se creó `admins/{uid}` para la cuenta admin actual (`marcosfenollar@gmail.com`) usando la API de administración de Firebase (bypass de reglas, sin ventana insegura intermedia) antes de desplegar la regla endurecida, para no perder acceso al propio panel.
  3. **Mismo problema existía sin explotar en `/admin` y `/tpv`:** ambos solo comprobaban "¿hay sesión de Firebase Auth?", no "¿es admin?" — cualquier cliente logueado que navegara directamente a esas rutas habría visto (aunque las reglas ya le bloquearían las escrituras) el dashboard. Añadido el mismo guard de `checkIsAdmin(uid)` a `AdminApp.jsx` y `PosApp.jsx`: si hay sesión pero no es admin, pantalla de "esta cuenta no tiene acceso" con botón de cerrar sesión, en vez del dashboard.

  5. `src/lib/auth-service.js`: `login`/`signup` genéricos (mismo Firebase Auth que ya usaba el admin). `src/lib/firestore-service.js`: `checkIsAdmin`, `subscribeToMyOrders`/`subscribeToMyAppointments` (filtradas por `userId`, ordenadas en cliente para no depender de un índice compuesto), `getCustomerProfile`/`saveCustomerProfile`; `placeOrderTransaction` y `createAppointment` ahora adjuntan `userId` automáticamente cuando `auth.currentUser` existe.
